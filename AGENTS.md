# My DAW: правила для агентов разработки

## Сначала готовое решение

Приоритет владельца: развивать продукт, а не писать с нуля то, что уже надёжно
реализовано в поддерживаемых библиотеках и SDK. Это правило действует для новых
функций, исправлений и рефакторинга во всём репозитории.

Перед реализацией общего механизма:

1. Найти существующий путь в проекте, чтобы не создавать вторую реализацию.
2. Проверить возможности стандартной библиотеки и системных SDK.
3. Рассмотреть уже подключённые зависимости, затем подходящие готовые библиотеки.
4. Собственную реализацию выбирать только при конкретном неподходящем контракте,
   ограничении лицензии, платформы, задержек или неоправданной стоимости интеграции.

Для существенного выбора кратко указать в PR: что переиспользуем, ссылку на
первоисточник, проверенную версию, ограничения и причину собственного кода,
если он всё-таки нужен. Не превращать мелкие исправления в отдельное исследование.

## Границы интеграции

- Собственный код сосредоточить на UX, модели проекта, командах/undo и тонких
  адаптерах между готовыми компонентами. Не дублировать их внутренние механизмы.
- В первую очередь искать готовое решение для DSP, ресемплинга, кодеков,
  time-stretch/pitch-shift, plugin hosting, парсеров форматов и инфраструктуры.
- Не добавлять тяжёлую зависимость ради тривиальной функции, уже доступной в SDK.
- Проверять сопровождение, совместимость с macOS/arm64, лицензию, размер,
  зависимости и поведение при ошибках; популярность сама по себе не доказательство.
- Сохранять native UI и существующие domain/audio/C ABI/storage границы.
  Использование библиотеки не означает перенос всего приложения на её framework.
- В audio callback не добавлять locks, allocation, file I/O или destruction.
  Сторонний код также должен удовлетворять этому контракту на используемом пути.
- Рабочую реализацию заменять по одному модулю, с regression/parity fixtures
  и измерениями, а не глобальной переписью. Локальное исправление допустимо,
  когда миграция несоразмерна задаче.

## Зависимости и доказательства

При выборе и обновлении сверять API и версии с официальными источниками.
Предпочитать актуальный совместимый стабильный выпуск; develop/pre-release
требует явной причины и exact revision. Не подменять upstream-pinned submodules
без отдельной проверки совместимости. Обновлять lockfile, bootstrap/build scripts
и notices согласованно; не скачивать незакреплённый latest во время обычной сборки.

Соблюдать [CONTRIBUTING.md](CONTRIBUTING.md),
[правила лицензирования](docs/13-open-source.md) и
[границы зависимостей](dependencies.lock.json). Spike-only зависимости не
переносить в поставляемое приложение без отдельного решения по совместимости
и лицензированию.

Проверять не только библиотеку отдельно, но и её интеграцию с DAW: реальный
публичный путь, обработку ошибок и применимые save/open, undo, timing и latency
контракты. В отчёте различать написанный код, выполненные тесты, пропуски и
блокеры. Компиляция, fake helper или создание PR не доказывают работу физического
MIDI, аудиоустройства, интерфейса или стороннего плагина.
