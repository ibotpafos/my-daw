# Асинхронный playback prepare и AUv3 OOP — 1.26.0

Этот срез продолжает B-012 и подключает первый настоящий runtime isolation path. Для AUv3 пользователь может выбрать `Запрос OOP (AUv3)`. Host вызывает асинхронный `AudioComponentInstantiate` с `kAudioComponentInstantiation_LoadOutOfProcess`, ожидает completion только на bounded background worker и после создания проверяет read-only `kAudioUnitProperty_LoadedOutOfProcess`. Если система вернула in-process instance, property недоступно или истёк десятисекундный timeout, instance освобождается, insert остаётся dry/unavailable и error попадает в telemetry. AUv2 и VST3 по-прежнему не рекламируют OOP.

`Play` больше не строит render graph на AppKit main thread. Новый двухфазный `Output` сначала выполняет `prepare` без открытия hardware, затем control thread принимает только результат с совпадающими project revision и transport generation и вызывает `startPrepared`. Stop, seek, loop, open, recording и изменения проекта отменяют либо делают stale текущую подготовку. Detached worker владеет копией `State` и shared result, не хранит указатель на `daw_session`; закрытие сессии не ждёт completion. Общий лимит background jobs применяется и к playback prepare.

Во время работы UI показывает `Подготовка render graph и плагинов…`, блокирует повторный Play и оставляет Stop доступным для отмены. Ошибка hardware start переводит transport в отдельное состояние preparation failure, поэтому Play не остаётся навсегда выключенным. Generic parameter editor намеренно выключен для OOP insert: remote parameter proxy ещё не реализован, а скрытое создание второго in-process instance нарушило бы выбранную политику.

QA полного набора обнаружил ещё два audio regression. Обычный channel gain ошибочно перемножал три стартовые smoothing ramp и создавал кубическую атаку; теперь неавтоматизированный путь использует один already-combined smoothed gain. При callback, закончившемся точно на `loopEnd`, transport преждевременно показывал `loopStart`; теперь boundary остаётся видимой до следующего render block.

Проверены C++/C сборка, семь автоматических suites, локальный bundle и видимый Play/Stop lifecycle на QA draft. Быстрое воспроизведение без тяжёлого AUv3 не позволило удержать состояние `PREPARING` на экране; для этого нужен отдельный прогон с медленно создаваемым установленным компонентом. Фактическое размещение конкретного AUv3 и звук зависят от установленного компонента; vendor compatibility, прослушивание и hardware presentation latency остаются отдельными gates.
