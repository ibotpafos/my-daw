# Dry recording — 0.8.0

14 сентября 2026. Кнопка «● Запись» захватывает default mono-вход Core Audio и после Stop добавляет новый аудиотрек в позицию курсора. Дубль становится обычным неизменяемым `Clip`: его можно воспроизвести, переместить, разрезать, отменить через Undo и сохранить в текущем SQLite-черновике v5.

## Пользовательский поток

1. Пользователь ставит курсор на таймлайне и нажимает «● Запись».
2. Только это действие проверяет системное разрешение микрофона. При первом запуске macOS показывает штатный запрос; отказ не запускает аудиоустройство и объясняется в интерфейсе.
3. Playback останавливается, проектные контролы блокируются, а транспорт показывает длительность принимаемого дубля.
4. «■ Закончить» останавливает Audio Unit, создаёт дорожку `Запись N` и одну Undo-команду. Save, закрытие или смена проекта сначала заканчивают активный дубль.
5. При заполнении bounded-буфера запись автоматически заканчивается; принятые кадры сохраняются как клип.

Вход должен работать на 48 кГц. При другой nominal sample rate приложение просит изменить её в Audio MIDI Setup и не делает скрытый realtime resampling. Первый срез пишет один mono-канал и дублирует его в stereo-контейнер движка. Начиная с [1.8.0](33-full-duplex-loop-recording.md), armed loop recording воспроизводит проект и создаёт несколько takes; выбор канала, pre-roll, metronome и latency compensation пока отсутствуют.

Текущая локальная сборка подписана ad-hoc: на машине нет установленной Apple Development/Developer ID identity. Поэтому после изменения бинарника macOS может считать его новой code identity и снова спросить доступ к микрофону. Build script уже принимает `DAW_SIGNING_IDENTITY`; постоянство TCC между сборками требует настоящей стабильной подписи. Подменять designated requirement одним bundle identifier нельзя.

## Граница realtime

До запуска выделяется непрерывный буфер максимум на 60 секунд. Фактическая ёмкость дополнительно ограничена оставшимися 10 минутами таймлайна и лимитом 64 MiB аудио в прототипе. Core Audio callback вызывает `AudioUnitRender` в заранее выделенный scratch и копирует кадры в capture buffer. В callback нет файловых операций, SQLite, mutex, Swift Tasks и выделения памяти.

После `AudioOutputUnitStop` control thread копирует принятую часть в неизменяемый `Clip`, строит cached peaks и коммитит новый `State`. Значения NaN превращаются в тишину, а выходящие за внутреннюю защитную границу samples ограничиваются до диапазона Clip. Смена или отключение default input обнаруживается при UI-poll, после чего запись отменяется с явной ошибкой.

## Данные и восстановление

Завершённый дубль использует существующую схему проекта v5, поэтому отдельная миграция формата не нужна. Save/recovery после Stop включает PCM, Region и позицию записи. Undo удаляет добавленную дорожку, Redo возвращает её через shared immutable media.

Активный дубль живёт только в памяти процесса. Падение приложения, принудительное завершение или отключение устройства до Stop теряет незавершённую запись. Поэтому этот срез доказывает input → model → save, но ещё не закрывает требование B-007 о recoverable media. Следующая реализация записи должна использовать bounded ring и recoverable chunk writer, описанные в [аудиодвижке](05-audio-engine.md).

## Проверка

Debug CTest проверяет bounded capture на синтетическом mono-сигнале: stereo duplication, NaN sanitization, защитный clamp, overflow, создание `Clip`, позицию Region, Undo и idle C ABI. Все существующие storage/render/bridge тесты продолжают проходить. Swift 6 приложение собрано с `AVFoundation`, `AudioToolbox` и `CoreAudio`; `Info.plist` содержит объяснение доступа к микрофону.

Автоматическая проверка не нажимала Record, поэтому не вызывала системный запрос разрешения и не использовала микрофон пользователя. Ещё нужны ручной входной smoke, прослушивание записанного дубля, USB disconnect/sample-rate scenarios, loopback latency и длительная запись. До этих проверок нельзя считать физический recording path принятым.
